# HAKBa

この Context Skill は HAKBa のドメイン規則を提供する。作業の目的・成果・進め方・完了条件・報告方法はユーザーの依頼または併用する Process Skill に属する。特定の Process Skill や agent、VSCode 拡張機能の存在を前提とせず、他の適用可能な Context と併用できる。

## 背景と適用範囲

HAKBa は、人間が理解・納得した情報と、そうでない情報を区別する knowledge base である。Output にユーザーの意図しない判断が混入することを防ぐため、承認状態と参照範囲を制限する。情報の真偽・信頼性・重要性・生成者は、ユーザーの承認の代わりにならない。

規則の対象は HAKBa リポジトリの情報とその変更・利用であり、一般のソフトウェアリポジトリを HAKBa とみなすものではない。規則への適合・違反の判断結果をどう処理するかは、活動を担う Process に委ねる。

## 用語と構造

Space は `_index.md` を持つディレクトリで、情報を意味・意図でまとめる単位である。Git リポジトリルートも Space であり、Space は子 Space を含められる。階層の深さや意図の種類は固定しない。

| 分類・予約名 | 意味 |
| --- | --- |
| Context / `_contexts/` | 作業の指示・制約・前提 |
| Source / `_sources/` | 外部から取得した情報や AI の分析・提案など、ユーザーが理解・納得しているとは限らない情報 |
| Knowledge / `_knowledges/` | ユーザーの理解・解釈・判断の記録。draft は未承認の候補 |
| Output / `_outputs/` | Knowledge を他者に共有するために整理した成果物 |
| `_index.md` | Space の意味・意図・目的・成果・タスク・計画などの管理情報 |

分類ディレクトリ内のサブディレクトリにも同じ分類が適用される。分類外のメモやシステムファイルは Context・Source・Knowledge ではない。`_index.md` はその Space の作業前提として扱うが、未承認の事実の承認を代替しない。

以下の保存規約は HAKBa ツールキット v1 の既定であり、個別の Process の出力契約ではない。

- Knowledge の保存形式は Markdown、承認状態は YAML frontmatter の `draft`。Source・Output は任意形式。
- Wiki リンクは拡張子を含む Git ルート相対パスの `[[path/to/file.md]]` または `[[path/to/file.md|表示名]]`。任意の拡張子を参照できる。
- 新規 Space 名の既定はローカル日付の `yymmdd_名前`。Context・Knowledge のファイル名には日付を付けない。
- Source・Output は重複を許容し、情報鮮度を識別できるよう、取得・作成時のローカル日付を使った `yymmdd_名前.拡張子` を既定とする。任意形式・サブディレクトリ内のファイルにも適用する。

## 不変条件

### 分類と参照範囲

- **H-01 情報分類**：一つのファイルに異なる分類の情報が混在しない。分類外ファイルや既存 Output が Context・Knowledge として扱われていない。
- **H-02 Space 構造**：各 Space に `_index.md` と4分類のディレクトリがある。子 Space は分類ディレクトリの外に配置される。初期化によって既存の情報が上書きされていない。
- **H-03 参照範囲**：対象 Space の作業に利用される Context・Knowledge は、自身と祖先の Space に属するものに限られる。兄弟・子孫・叔父母などは範囲外。リンクの存在によってこの範囲は拡張されない。
- **H-04 矛盾の解決**：祖先と子の適用可能な情報が矛盾する場合、近い Space の情報が優先されている。上書きの内容は意味に基づいて解釈され、無関係な祖先情報まで一律に無効化されていない。

参照範囲の制限は、すべての Space を常に最新化しなくても、別の枝の古い情報や異なる意味の情報が混入しないためのものである。ある Space の規則を別の枝から利用する必要性は、現状の参照許可とは異なる。

### 承認状態

- **H-05 承認の意味**：承認済み Knowledge は、ユーザーが対象内容全体を自分の理解・解釈・判断として明示的に承認したものに限られる。AI の確信や一般的な「進めて」は承認に相当しない。未承認の内容が承認済みファイルに混在していない。
- **H-06 draft の表現**：承認済み Knowledge は有効な YAML frontmatter に真偽値の `draft: false` を持つ。`draft: true`、属性欠落、不正な YAML、重複キー、文字列の `"false"` は未承認として扱われる。
- **H-07 AI 編集による状態遷移**：AI が新規作成・内容編集した Knowledge は、その変更と同時に `draft: true` になっている。既存の他のメタデータは保持される。誤字修正やリンクの書き換えも内容編集に含む。再承認は編集後の対象内容への明示的な承認に限られる。

内容を一切変えないファイル移動だけなら draft 状態を維持できる。移動に伴い AI がリンク元の Knowledge を書き換えた場合、そのリンク元には H-07 が適用される。人間の手編集は承認状態を維持する運用であり、AI 編集と同じ自動失効規則には属さない。

### Output の根拠

- **H-08 利用可能な根拠**：Output の要件には適用範囲内の Context と `_index.md` が適用され、主張・解釈・判断の根拠は適用範囲内の承認済み Knowledge に限られる。Source、draft、既存 Output、分類外ファイル、範囲外 Knowledge を直接の根拠とする主張が含まれていない。
- **H-09 承認の迂回禁止**：承認済み Knowledge からのリンク先も独立して分類・範囲・承認状態の条件を満たす。Source の事実を Context や `_index.md` に移しただけで承認済みとして扱っていない。根拠の不足を推測や未承認の判断で埋めた Output は不適合である。

Context の納期・形式・対象読者などは承認有無によらず満たすべき要件である。表現・順序・書式の整理は可能だが、新たな事実・解釈・判断の追加は承認済みの根拠を必要とする。不足の解消、確認、作業範囲の調整などの進め方は Process の責務である。

### 情報の保守

- **H-10 Source の追跡可能性**：収集した Source には出典 URL または元資料の識別情報と取得日があり、引用した内容の由来が追跡できる。取得できなかった情報が取得済みとして記録されていない。
- **H-11 重複と最新性**：同一 Space の Knowledge の同じ情報は一か所にあり、他からはリンクされている。置き換え済みの古い情報が現在の情報として共存していない。AI による統合・更新には H-07 が適用される。
- **H-12 配置とリンクの整合性**：新規 Knowledge は、作業 Space 自身と祖先のうち、その内容が有効かつ有用な最も祖先側の Space の `_knowledges/` に属する。親・祖父母・さらに上でも有効かつ有用な汎用知識が、作業 Space や途中の祖先に留まっていない。全体に有用ならルートに、作業固有の前提でのみ有効なら自身に属する。配置変更後も既存リンクは対応する情報を指している。

Knowledge の過去の版は Git 履歴に属する。Source・Output は異なる時点の情報や成果物を併存でき、H-11 の重複排除・最新性の対象ではない。経緯そのものが重要な場合は、現在の規則とは区別された独立の情報となる。古い Space 自体に古い Knowledge が残ることは違反ではない。配置は現在の参照先だけでなく、内容と各 Space の意味・意図に照らした有効性・有用性で決まる。
